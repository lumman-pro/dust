# DFS keyword completion: Elasticsearch 8.16 evidence

Research date: 2026-10-19. Target: one `dfs.objects` index on Elasticsearch 8.16.0 / Lucene 9.12.0. Requirements: completion while typing, quoted exact phrases, English/French stemming, required terms spanning filename/content/selected attributes, and modifiers such as `type:pdf`. This is source-based design research. The companion Elasticsearch experiments establish the empirical behavior separately. [Pinned dependency versions](https://github.com/elastic/elasticsearch/blob/v8.16.0/build-tools-internal/version.properties)

**Recommendation:** keep an unstemmed Unicode text representation for phrases and prefixes, separate English/French representations for completed-word matching, and explicit filename component analysis. Use `index_prefixes` on the unstemmed fields as a prefix-query accelerator. Compile the search expression into required term/phrase groups with field-specific alternatives and independent scores. This supports the requested behaviors together. Changing a field to `search_as_you_type` or appending `*` to an entire expression does not supply the query semantics by itself.

## One mapping, one query plan

The proposed [settings](dfs.objects_1.settings.proposed.json) and [mapping](dfs.objects_1.mappings.proposed.json) implement this separation:

| Purpose | Representation | Query responsibility |
| --- | --- | --- |
| Natural-language words, phrases, and completion | Unstemmed ICU-tokenized/folded `name`, `content_text`, and selected textual attribute fields | Whole-token matches, `match_phrase` with zero slop, and analyzed prefix queries |
| Filename components | Unstemmed `name.parts`, split at filename delimiters/case transitions before folding | Match components and their prefixes without deleting the original basename or its suffix |
| English/French inflections | Flat sibling `.en` / `.fr` fields. Filename variants use component analysis | Completed-word alternatives, preferably grouped with `dis_max` to limit repeated evidence |
| Identity and exact modifiers | Raw `name.keyword`, normalized keyword fields, typed dates/IDs | Exact equality and hard filters |

Multi-fields index the same original value using separate mappings. Their options are not inherited from the parent, and they do not add copies to `_source`. Keep siblings such as `name.parts`, `name.en`, and `name.fr`. Do not model a multi-field under another multi-field. Tags can have sibling `tags.text`, `tags.en`, and `tags.fr` representations. [8.16 multi-fields](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/mapping/params/multi-fields.asciidoc)

For `type:pdf quarterly repo`, the conceptual plan is:

1. Apply authorization/scope constraints and the parsed PDF type filter.
2. Require `quarterly` through at least one eligible filename, body, or selected-attribute word representation, including the language alternatives.
3. Require the active `repo` completion through an unstemmed prefix alternative in those fields, so `reports` is eligible.
4. Rank with independent field scores plus chosen exact-name/whole-word/phrase preferences.

Each required group may match a different field. A quoted clause instead requires its complete unstemmed phrase within a single field/value. It must not be reconstructed across filename, body, or two tags. A prohibited clause excludes its intended alternatives. A modifier is a typed filter, not a searchable word. These are proposed product semantics, not an existing DFS API constraint. Elasticsearch `bool` provides the required conjunction/disjunction/filter primitives. [Boolean query](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/query-dsl/bool-query.asciidoc)

The parser must identify the active unquoted word before compiling the expression. Closed quotes and `type:pdf` are never automatically prefixed. Preserve the distinction between an active word and one terminated by whitespace. Do not silently lose it by trimming before parsing. Decide explicitly what submission does to the active word: a completion that disappears immediately on submit is surprising. If submission retains the prefix alternative and adds completed-word stemming, it preserves that candidate set while enabling inflection matching. Applying a stemmer to an unfinished word is not the same operation.

## Prefix mechanisms: what changes and what does not

| Mechanism | Exact 8.16 behavior | Assessment for this index |
| --- | --- | --- |
| Manually indexed `edge_ngram` field queried with `match` | Only stored grams can match. `preserve_original` additionally stores the full token, but not every missing intermediate prefix beyond `max_gram` | A finite gram range can leave a recall gap. Truncating queries changes meaning. Root-field prefix fallback would have to be designed explicitly |
| `text` plus `index_prefixes` | Keeps ordinary full tokens and adds an internal prefix field. In-range prefix queries use indexed prefixes. Out-of-range queries fall back to the ordinary root-field prefix query | Good fit for independent filename/body/attribute fields. The configured maximum bounds acceleration, not prefix recall, provided fallback queries are allowed |
| `search_as_you_type` | Adds shingle fields and an internal prefix field over the largest shingles. Its root also keeps full tokens and supports long-prefix fallback | Useful when adjacent-word completion/order ranking warrants those extra representations. It is not intrinsically more correct for cross-field eligibility or bilingual stemming |
| Plain `text` prefix query | Expands against the root term dictionary without a pre-indexed prefix representation | A valid baseline for measuring whether body prefix indexing earns its ingestion/storage cost |

Sources: [edge-ngram limits](https://www.elastic.co/guide/en/elasticsearch/reference/8.16/analysis-edgengram-tokenfilter.html), [Lucene gram/original emission](https://github.com/apache/lucene/blob/releases/lucene/9.12.0/lucene/analysis/common/src/java/org/apache/lucene/analysis/ngram/EdgeNGramTokenFilter.java#L89), [text prefix rewrite](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/mapper/TextFieldMapper.java#L774), [search-as-you-type design](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/mapping/types/search-as-you-type.asciidoc).

`index_prefixes.max_chars` must be below 20. Its documented default is 5. The search-as-you-type implementation internally uses 1–20-character grams and also falls back beyond its acceleration range. Query the public root field, not its internal `._index_prefix`: the public field owns this fallback. Neither mechanism promises arbitrary substrings inside a token. Search-as-you-type's “infix” support concerns terms occurring later in the text. [Prefix configuration validation](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/mapper/TextFieldMapper.java#L123), [search-as-you-type defaults/rewrite](https://github.com/elastic/elasticsearch/blob/v8.16.0/modules/mapper-extras/src/main/java/org/elasticsearch/index/mapper/extras/SearchAsYouTypeFieldMapper.java#L342)

**Operational boundary:** an out-of-range fallback reaches `StringFieldType.prefixQuery`, which rejects execution when `search.allow_expensive_queries` is false. Thus enabling `index_prefixes` does not guarantee that every possible prefix works under that setting. The optimized path normally has constant-score behavior. A prefix-only match is not an ordinary BM25 word match. Keep whole-word and filename ranking signals available. [Fallback and setting check](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/mapper/StringFieldType.java#L95), [optimized constant-score wrapping](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/mapper/TextFieldMapper.java#L783)

The proposed ranges (`min_chars: 1`, filename/title maximum 10, body/description maximum 5) are reasonable initial acceleration budgets, not measured optima. The body is the largest cost exposure: its prefix analyzer emits additional terms after the complete root analysis, and the internal field copies index options while omitting norms. With offsets enabled, the prefix field also carries those postings details. Do not select a large maximum on every body merely because the mapping accepts it. Search-as-you-type would additionally materialize shingles. Measure index size, ingestion throughput, and short-prefix latency with representative extracted bodies. [Text prefix field construction](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/mapper/TextFieldMapper.java#L406), [prefix analyzer](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/mapper/TextFieldMapper.java#L522), [search-as-you-type analyzer](https://github.com/elastic/elasticsearch/blob/v8.16.0/modules/mapper-extras/src/main/java/org/elasticsearch/index/mapper/extras/SearchAsYouTypeFieldMapper.java#L797)

## `match_bool_prefix` is analyzed, but not a whole-query solution

`match_bool_prefix` analyzes its input, uses ordinary term queries for preceding tokens, and a prefix query for the final eligible token. It delegates to the field mapper, so `index_prefixes` acceleration/fallback applies. A raw `prefix` query does not perform that full analysis. Its `case_insensitive` option is ASCII-only. Use the unstemmed field's analyzer for Unicode folding/tokenization rather than expecting that option to normalize French input. [8.16 match-boolean-prefix](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/query-dsl/match-bool-prefix-query.asciidoc), [query construction](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/search/MatchQueryParser.java#L502), [prefix query parameters](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/query-dsl/prefix-query.asciidoc#L44)

The implementation checks token offsets: it prefixes the final simple token only when its end offset reaches the end of the analyzed input. Trailing whitespace/punctuation can therefore change the query to a complete-term match. It also deliberately avoids prefixing stacked synonym alternatives. A search analyzer combining originals/stems/synonyms at one position can change completion behavior unexpectedly. Separate representations avoid requiring such a combined token stream for completion. [Final-token and synonym handling](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/search/MatchQueryParser.java#L513)

Whole-query `multi_match` with `type: bool_prefix` remains field-centric. With `AND`, it can require all analyzed terms within one field and lose the filename/body split case. The standard search-as-you-type query template does not solve that either. Compile the required concept groups first. Use prefix matching within the active group's field alternatives. Likewise, a prefix clause added only as an optional boost cannot admit a document rejected by a mandatory whole-word clause. [Multi-match field-query construction](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/search/MultiMatchQueryParser.java#L51)

## English and French in one index

**Recommended v1:** use one object index with an unstemmed root plus English/French alternatives on selected text fields. For the current proposed settings, English uses `porter2` and French uses `light_french`. Porter2 is an explicitly supported ES stemmer implemented with Snowball's English stemmer. This is a broader inflection choice than KStem, justified when `run` and `running` must match. KStem's dictionary contains `running`, and its implementation returns such dictionary entries unchanged. “light English” does not guarantee that pair. [8.16 stemmer dispatch](https://github.com/elastic/elasticsearch/blob/v8.16.0/modules/analysis-common/src/main/java/org/elasticsearch/analysis/common/StemmerTokenFilterFactory.java#L140), [KStem dictionary entry](https://github.com/apache/lucene/blob/releases/lucene/9.12.0/lucene/analysis/common/src/java/org/apache/lucene/analysis/en/KStemData6.java#L744), [dictionary early return](https://github.com/apache/lucene/blob/releases/lucene/9.12.0/lucene/analysis/common/src/java/org/apache/lucene/analysis/en/KStemmer.java#L1755)

Use possessive normalization in the English prose alternate and French elision in the French prose alternate before stemming. French elision handles both straight and curly apostrophes, e.g. `l'avion`. The standard French analyzer combines it with `light_french`. Keep stop-word removal off initially so required-word eligibility does not depend on inconsistent per-field stop lists. The unstemmed roots retain ordinary words for quotes. [Elasticsearch English/French analyzer recipes](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/analysis/analyzers/lang-analyzer.asciidoc#L630), [Lucene elision handling](https://github.com/apache/lucene/blob/releases/lucene/9.12.0/lucene/analysis/common/src/java/org/apache/lucene/analysis/util/ElisionFilter.java#L45)

Indexing both languages everywhere is a deliberate recall-first tradeoff for unlabeled and mixed-language objects. It adds two complete analyzed body representations and can introduce cross-language stem collisions. Group variants of the same evidence rather than blindly summing all of them. Exact unstemmed matches can receive stronger preference. These choices do not prove the best boosts or absence of false positives.

Language-gated body indexing requires explicit derived physical fields populated from classified text. A query-time language filter cannot undo the postings already created by multi-fields. Segment-level classification can retain both languages within mixed documents, whereas a single dominant-document label can discard minority-language stemming. With no established reliable classifier in the current projection, language gating is a later storage/precision optimization with its own recall tests. Separate language indexes add cross-index/object-coordination work without resolving mixed-language content. These are design deductions, not Elasticsearch requirements.

## Filename punctuation, exact phrases, and modifiers

Keep the complete basename. An unstemmed ICU root preserves a useful multilingual word view. A separate component view makes dots, underscores, hyphens, and CamelCase searchable. `word_delimiter_graph` should receive punctuation from a whitespace or keyword tokenizer, and case splitting must happen before case folding. The proposed component analyzer disables numeric splitting to retain identifiers such as `Q4`/`OAuth2`, and does not concatenate or preserve the original in that same token stream: the other fields already retain it. Stem the component representation for filename `.en`/`.fr`. Stemming a single ICU token such as `CamelCaseReport.pdf` cannot manufacture the component `report`. [Word-delimiter rules and tokenizer guidance](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/analysis/tokenfilters/word-delimiter-graph-tokenfilter.asciidoc#L7)

**Apostrophe boundary recommendation:** the plain ICU root can retain `l'avion` as one token, preventing `avio` from prefix-matching it. Map straight/curly apostrophes to spaces in the unstemmed root's character filter, retaining language-specific elision in the stemmed alternate. This also exposes `Reilly` inside `O'Reilly` and preserves the `l` token in a quoted `"l'avion arrive"`. Common-root elision would instead allow that quote to match `"avion arrive"`. The character-filter approach needs no fourth indexed representation. It deliberately defines apostrophes as word boundaries, so test contractions, possessives, quoted phrases, and active prefixes before adoption. Elasticsearch's mapping character filter performs this substitution before tokenization. [Mapping character filter](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/analysis/charfilters/mapping-charfilter.asciidoc)

**Quoted exact phrase means consecutive normalized, unstemmed tokens at zero slop**, not byte-for-byte text equality. ICU folding can equate case/diacritics and tokenization can treat punctuation as boundaries. A stricter accent/punctuation-preserving phrase requirement would require a different literal representation. Keep closed quotes away from stemmed/prefix alternatives, and keep full-basename equality on `name.keyword`. Changing only the search quote analyzer cannot restore words removed or transformed by an index-time stemmer. [Multi-field exact/stemmed example](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/mapping/params/multi-fields.asciidoc#L73)

Selected xattributes should project through a small typed allowlist: textual title/description/tag search, keyword owners/source/tags, and validated dates. Arbitrary byte-valued xattributes remain separate from this friendly search representation. `type:pdf` should compile to a defined file-type filter. Define how MIME and extension derive that type and how conflicts are handled. Extracting an extension for that purpose does not require deleting it from searchable filenames. These are projection/parser responsibilities, not analyzer settings.

For friendly exact-name/tag matching, use the same intended Unicode normalization consistently. `icu_folding` is implemented as a normalizing token-filter factory and can serve a custom keyword normalizer. A lowercase/ASCII-folding keyword path should not be assumed equivalent to the ICU text path. Test NFC/NFD accents explicitly. Preserve the raw keyword alongside any friendly normalization. [ICU folding factory](https://github.com/elastic/elasticsearch/blob/v8.16.0/plugins/analysis-icu/src/main/java/org/elasticsearch/plugin/analysis/icu/IcuFoldingTokenFilterFactory.java#L37)

## Unicode and synonym boundaries that need explicit tests

The 8.16 text-prefix mapper tests Java `String.length()` (UTF-16 code units), while Lucene's edge-ngram filter counts Unicode code points. With `min_chars: 2`, a one-code-point supplementary prefix such as `𠮷` can take the direct indexed-prefix path even though no one-code-point prefix was indexed. `min_chars: 1` avoids that lower-bound mismatch. Supplementary characters may still trigger the long-prefix fallback earlier than the nominal code-point range. Test both query correctness and the expensive-query setting. Do not advertise the acceleration range as a Unicode character guarantee. [Mapper bound checks](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/mapper/TextFieldMapper.java#L577), [Lucene code-point counting](https://github.com/apache/lucene/blob/releases/lucene/9.12.0/lucene/analysis/common/src/java/org/apache/lucene/analysis/ngram/EdgeNGramTokenFilter.java#L99)

Do not treat arbitrary whitespace splitting as equivalent to language analysis. A syntactic word can generate multiple tokens (French apostrophes, identifiers, non-space-delimited scripts). Decide whether that is an atomic group or several required concepts, and test cross-field behavior accordingly. Keep phrase text intact. Synonym graphs are intended for search-time analysis, but splitting a multiword expression before analysis prevents a synonym rule spanning it. Future synonyms need their own complete-word/query-graph path. Putting them into the active prefix analyzer is unsafe because of the stacked-synonym behavior above. `word_delimiter_graph`/ngram filters before synonym parsing can also be invalid. [Synonym graph and filter-order rules](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/analysis/tokenfilters/synonym-graph-tokenfilter.asciidoc#L155)

## Acceptance cases and future ranking

The minimum diagnostic set should include `repo`→`reports`, short and beyond-range prefixes, `run`/`running`, French inflections/elisions, quoted singular versus plural phrases, required words split across all three source categories, exact modifiers, filename suffixes/CamelCase/identifiers, composed/decomposed accents, and the supplementary-character bound case. Compare the same query under missing versus very long unrelated bodies, and include mixed English/French documents and deliberate stem collisions. Evaluate prefix latency and index size separately from correctness.

Keep the independent text fields, token counts, content/extraction state, and authoritative modification timestamps accessible for later LTR features. Do not add LTR now or make candidate inclusion depend on future reranking. Derived date fields used for freshness must not reject otherwise valid objects whose authoritative unsigned millisecond values lie outside Elasticsearch's date domain. Retain the raw value and define missing derived dates. The earlier [ranking evidence](dfs-search-ranking-evidence.md) records native-LTR licensing, per-shard rescore windows, and pagination constraints.
