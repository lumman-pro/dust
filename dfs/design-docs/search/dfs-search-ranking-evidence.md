# DFS retrieval and reranking: Elasticsearch 8.16 evidence

Research date: 2026-10-19. Target: `dfs.objects` on Elasticsearch 8.16.0, with the infrastructure's reported Basic license. Elasticsearch pins Lucene **9.12.0**, so the implementation evidence below uses that release. This note makes no claim about Google Drive's internal implementation. A companion local synthetic diagnostic checks mechanics; production relevance, latency, and the live cluster license remain unmeasured here. [Pinned dependencies](https://github.com/elastic/elasticsearch/blob/v8.16.0/build-tools-internal/version.properties)

**Recommendation.** Start full keyword search with separately analyzed and scored filename/body fields, term eligibility that can span fields, and explicit filename ranking signals. Elasticsearch's `simple_query_string` inside a `bool` query is a concrete candidate for this design. A lone scored `combined_fields` query is a weak default for short filenames attached to long bodies: its shared length normalization can penalize a filename match for unrelated body text. A `copy_to` catch-all has the same structural concern. Keep both as benchmark alternatives; neither is a prerequisite for LTR. Begin with measurable lexical ranking and optional query rescore; native LTR requires a different license and a trained model.

It runs a second query over a bounded candidate window and combines scores with configurable weights. Suitable for a Basic-compatible baseline. [8.15 GA announcement](https://www.elastic.co/blog/whats-new-elastic-search-8-15-0), [8.16 config](https://github.com/elastic/elasticsearch/blob/v8.16.0/x-pack/plugin/core/src/main/java/org/elasticsearch/xpack/core/ml/inference/trainedmodel/LearningToRankConfig.java#L233), [enforcement](https://github.com/elastic/elasticsearch/blob/v8.16.0/x-pack/plugin/ml/src/main/java/org/elasticsearch/xpack/ml/action/TransportPutTrainedModelAction.java#L513) |

## What the scoring implementations actually combine

**Verified `combined_fields` behavior:** its term-centric eligibility lets each required term occur in any participating field. Fields must be `text` and have the same **search analyzer**; BM25 is required, per-field similarities are rejected, and field boosts must be at least 1. Lucene also requires consistent norms settings across participating fields: disabling norms on names while retaining them on bodies is not a supported fix. [8.16 query documentation](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/query-dsl/combined-fields-query.asciidoc), [Elasticsearch validation](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/query/CombinedFieldsQueryBuilder.java#L299), [Lucene norm validation](https://github.com/apache/lucene/blob/releases/lucene/9.12.0/lucene/sandbox/src/java/org/apache/lucene/sandbox/search/CombinedFieldQuery.java#L295)

For a single query term, the bundled implementation computes a weighted sum of matching term frequencies. It also sums the weighted, decoded length norms of **all participating fields present on the document**, including fields that do not contain that term. The combined norm is quantized again. Thus `name^4` multiplies the name's contribution to both frequency and length; it does not independently multiply an ordinary name BM25 score by four. [Combined scorer](https://github.com/apache/lucene/blob/releases/lucene/9.12.0/lucene/sandbox/src/java/org/apache/lucene/sandbox/search/CombinedFieldQuery.java#L422), [weighted length aggregation](https://github.com/apache/lucene/blob/releases/lucene/9.12.0/lucene/sandbox/src/java/org/apache/lucene/sandbox/search/MultiNormsLeafSimScorer.java#L142)

Its synthetic collection statistics use the maximum field document count, the weighted sum of total term frequencies, and the maximum per-field document frequency for the query term. These are approximations, not the exact statistics of a physically concatenated field: for example, the maximum per-field term document frequency need not equal the number of documents containing that term anywhere. This is the **simple** BM25F-style combination described in the docs, not independent field normalization followed by score addition. [Synthetic statistics](https://github.com/apache/lucene/blob/releases/lucene/9.12.0/lucene/sandbox/src/java/org/apache/lucene/sandbox/search/CombinedFieldQuery.java#L320)

**Derived consequence, not a benchmark result:** within a fixed corpus, two documents with the same matching filename and no matching body terms can score differently solely because one has a longer body. Missing body norms add no length; extracting a long body can therefore lower a filename-only match's score. BM25's default length-normalization coefficient is `b=0.75`. The magnitude and relevance impact depend on the corpus, boosts, and norm quantization. A filename boost may mitigate the effect but does not remove its cause. [BM25 normalization](https://github.com/apache/lucene/blob/releases/lucene/9.12.0/lucene/core/src/java/org/apache/lucene/search/similarities/BM25Similarity.java#L171)

**Verified `copy_to` behavior:** it copies the original field values, not their analyzed tokens; the target mapping therefore analyzes those values independently. The original fields remain independently searchable. Copied values are not added to `_source`, and copies do not propagate recursively through intermediary fields. A strict mapping must explicitly declare the target. [8.16 `copy_to`](https://www.elastic.co/guide/en/elasticsearch/reference/8.16/copy-to.html)

**Design consequences:** retaining indexed originals plus a catch-all adds analysis and another indexed representation, without duplicating `_source` merely because of `copy_to`. The catch-all's ordinary BM25 score mixes name/body length and term statistics and loses source-field identity. It cannot give names a distinct analyzer or score within that field. Separate name queries can restore those signals. Elastic recommends searching fewer fields as a speed optimization and identifies `copy_to` as one technique; this is not a measured latency or storage result for our workload. [8.16 search-speed guidance](https://www.elastic.co/guide/en/elasticsearch/reference/8.16/tune-for-search-speed.html)

## Field-aware alternatives and their limits

| Query | Verified behavior | Implication for filenames and bodies |
| --- | --- | --- |
| `multi_match: best_fields` | Builds independent field queries and selects their best score, optionally adding a fraction of other scores | Filename scoring keeps its own length norm and corpus statistics; a long nonmatching body does not enter that name score |
| `multi_match: most_fields` | Scores independent field queries and adds their contributions | Useful for complementary evidence or analyzed variants, but duplicated representations can repeatedly reward the same evidence |
| Whole-query `best_fields` / `most_fields` with `AND` | Requires all analyzed terms within one field; `minimum_should_match` is also applied per field | Loses a document whose required words are split between filename and body; neither is a sufficient full keyword backbone by itself |
| `multi_match: cross_fields` | Groups fields by analyzer and blends term statistics within each group | Cross-field eligibility only works within a group; mixed filename/body analyzers can reintroduce the per-group coverage problem |

These behaviors follow the [8.16 multi-match documentation](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/query-dsl/multi-match-query.asciidoc#L105) and [field-query construction](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/search/MultiMatchQueryParser.java#L81). Independent field scores still need calibration: name/body IDF and length distributions differ, and a rare incidental filename term can score strongly. Independent normalization is a useful control, not proof of superior ranking.

`cross_fields` is not an automatic replacement for `combined_fields`. Its final term queries retain individual field norms but receive altered term statistics before a `dis_max` combination. Elastic explicitly warns that this blending is generally useful for short fields with unit boosts, and can score incorrectly when some documents lack some fields. That is a poor presumptive fit for short names, long optional bodies, and asymmetric boosts. [8.16 cautions](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/query-dsl/multi-match-query.asciidoc#L376), [blended-term implementation](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/lucene/queries/BlendedTermQuery.java#L344)

## A concrete full keyword backbone with different analyzers

**Verified source behavior:** with `WHITESPACE` enabled, Lucene's simple-query parser splits ordinary input into syntactic terms and invokes `newDefaultQuery` separately for each one. Elasticsearch delegates each invocation to a multi-match query. Without an explicit analyzer override, each field uses its mapped search analyzer. With `default_operator: "and"`, the parser joins these term groups with required clauses. Therefore `quarterly budget` can match `quarterly` in the filename and `budget` in the body even when their analyzers differ, while scoring uses independent field norms. A term that itself analyzes into several tokens is handled inside its field query; this is not arbitrary cross-field mixing of those internal tokens. [Lucene 9.12 parser](https://github.com/apache/lucene/blob/releases/lucene/9.12.0/lucene/queryparser/src/java/org/apache/lucene/queryparser/simple/SimpleQueryParser.java), [8.16 parser override](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/search/SimpleQueryStringQueryParser.java#L80), [field query construction](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/search/MultiMatchQueryParser.java#L81)

In 8.16, `simple_query_string` defaults to **`MOST_FIELDS`**, so matching field scores add within each syntactic term. The source also accepts `type: "best_fields"` to choose the best field score per term, although `type` is absent from the archived public parameter table. If using that option, pin and test the target version rather than assuming every client/version exposes it. Quoted phrases take the separate `PHRASE` path, using field-specific phrase queries; they do not span a filename/body boundary. [8.16 builder defaults and type support](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/query/SimpleQueryStringBuilder.java#L90), [ordinary and phrase query paths](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/search/SimpleQueryStringQueryParser.java#L113)

Two consequences of analyzing syntactic words separately deserve explicit tests. Multiword synonym rules cannot span ordinary whitespace boundaries. If one field removes a stop word and another retains it, the remaining field alternative can make that word mandatory there; stop-word policies therefore affect eligibility as well as scoring. The proposed light stemming need not introduce either behavior. These are source-derived constraints, not reasons to combine unrelated field lengths. [Parser token boundaries](https://github.com/apache/lucene/blob/releases/lucene/9.12.0/lucene/queryparser/src/java/org/apache/lucene/queryparser/simple/SimpleQueryParser.java), [field-specific query construction](https://github.com/elastic/elasticsearch/blob/v8.16.0/server/src/main/java/org/elasticsearch/index/search/MultiMatchQueryParser.java#L81)

**Recommended starting semantics, not an existing API constraint:** use default `AND` for keyword input, permit explicit alternatives, quoted phrases, and exclusions, and keep authorization/scope constraints outside the user expression. A controlled flag set is `AND|OR|NOT|PHRASE|PRECEDENCE|WHITESPACE|ESCAPE`. Name and body fields are explicitly enumerated. Full basename equality and phrase/proximity evidence can be optional boosts on that required retrieval query. An analyzed quoted phrase is not byte-exact basename equality. The parser is fault-tolerant and ignores invalid syntax; verify its escaping and grouping behavior on filenames containing punctuation. Its documented default `OR` has surprising negative-term behavior, so it should not be inherited accidentally. [8.16 syntax and flags](https://www.elastic.co/guide/en/elasticsearch/reference/8.16/query-dsl-simple-query-string-query.html)

This is a **field-aware `bool` design**, but it need not start with a custom parser. If later semantics outgrow `simple_query_string`, the same explicit model can be compiled from an AST: each required word has field-specific alternatives; each required phrase must occur within one eligible field; exclusions are applied to the intended alternatives. The scoring policy can then choose the maximum or sum of independent field scores per word. Require a real lexical match: a `bool` containing scope filters and only optional scoring clauses defaults to `minimum_should_match: 0`. [8.16 Boolean semantics](https://www.elastic.co/guide/en/elasticsearch/reference/8.16/query-dsl-bool-query.html)

## Stemming and prefix variants change the retrieval plan

The same-search-analyzer restriction of `combined_fields` does not mean its fields must have identical index analyzers. However, forcing filename parts, natural-language stemming, and prefixes through one search analyzer just to satisfy that restriction gives up useful field-specific analysis. Independent field alternatives preserve it. Elastic documents `most_fields` for multiple analyzed forms of the same text, but adding variants also changes scores and storage; use deliberate weights or a best-alternative grouping rather than treating every representation as independent evidence. [8.16 analyzed-variant example](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/query-dsl/multi-match-query.asciidoc#L205)

**Recommended consequences:**

- A stemmed representation intended to improve recall must participate in the eligible alternatives. Making an unstemmed query mandatory and adding stemming only as a boost cannot retrieve stem-only matches.
- Preserve an unstemmed representation for exact-word/phrase preferences. `quote_field_suffix` can route quoted text to a corresponding field with different analysis; ensure the suffix mapping covers the fields actually queried. [8.16 quote-field option](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/query-dsl/simple-query-string-query.asciidoc#L120)
- Keep filename prefix retrieval separate from full-token body search. If an incomplete final word should admit a file, its prefix alternative must satisfy that word's eligibility; an optional prefix boost after a mandatory complete-word query cannot do so. Whether prefixes are requested explicitly or used during typing is a product choice.
- Do not apply every query term as a body prefix merely because edge n-grams are available. Prefix expansion, stemming, and literal terms have different recall/precision effects; they deserve separate evaluation and explanation.

These are design deductions. The best stemming strength, prefix limits, variant weights, and whole-query coverage policy require corpus evaluation. The source does not establish one universally best query or analyzer.

## What to benchmark before choosing weights and retrieval fields

| Comparison | Diagnostic case | Question it resolves |
| --- | --- | --- |
| Catch-all, combined fields, independent fields, and combined plus independent name boost | Identical matching filenames with absent, short, and very long unrelated bodies | How much does extraction/body length affect filename ranking? |
| Whole-query multi-match versus per-term field alternatives | Required words split across name/body with the same and different analyzers | Does eligible cross-field content survive? |
| Literal and stemmed alternatives | Exact names, identifiers, inflected prose, and stem-only relevant documents | Do variants improve recall without burying precise filename matches? |
| Full tokens versus explicit filename prefixes | Short prefixes, completed words, punctuation, and long filenames | Does prefix retrieval pollute full keyword results or miss intended files? |
| Independent name/body score sum versus best alternative | Repeated text across name/body and multiple analyzed variants | Is repeated evidence being over-rewarded? |
| Candidate windows and filtering | Missing extraction, directories, stale permissions, long documents, and different shard counts | Is sufficient relevant, authorized material available for ranking? |

Use synthetic cases to verify mechanics, then judged human and LLM keyword queries to measure recall at the candidate window, top-result ranking, latency, index size, and ingestion cost. Exact-name and strong filename signals belong in first-stage retrieval/ranking when needed to keep the intended file inside the candidate window. They should not be deferred exclusively to a reranker.

The [companion diagnostic results](dfs-keyword-search-diagnostic-results.json) use Elasticsearch 8.16.0, 215 synthetic documents, and one shard. They corroborate the predicted filename penalty for `copy_to`/`combined_fields`, stable filename-only scores with independent field scoring, and cross-field term eligibility with `simple_query_string` even under different analyzers. Whole-query `best_fields` with `AND` misses the split-field case. Compare scores **within a query** across the paired documents; absolute score magnitudes between different query constructions do not measure relative quality. These tests establish mechanics, not production ranking quality or latency.

## Candidate windows, recall, and pagination

Query rescore runs **on each shard before the coordinating node merges results**. `window_size` controls the top candidates rescored per shard; its default is only 10. With three searched shards and a window of 500, as many as 1,500 documents are rescored. That is not a global top-500 window. Explicit sorting other than descending `_score` is rejected, so the usual `[_score, object_id]` sort cannot simply be combined with this mechanism. Keep the window constant across pages. [8.16 rescore behavior](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/search/search-your-data/filter-search-results.asciidoc#L151)

Native LTR additionally makes the window mandatory and requires it to cover `from + size`. Its 8.16 implementation truncates each shard's candidate list to that window before applying model scores because first-pass and model scores are not comparable. [8.16 LTR usage](https://www.elastic.co/guide/en/elasticsearch/reference/8.16/learning-to-rank-search-usage.html), [rescorer implementation](https://github.com/elastic/elasticsearch/blob/v8.16.0/x-pack/plugin/ml/src/main/java/org/elasticsearch/xpack/ml/inference/ltr/LearningToRankRescorer.java#L61)

Derived consequence: final quality is bounded by first-stage matching and per-shard top-window recall. Evaluate both retrieval recall and final ranking quality; a better reranker cannot retrieve an excluded document. Permission and scope checks are eligibility constraints, not relevance features. If authoritative FDB checks reject stale candidates, bounded over-fetching/refilling also belongs in the end-to-end evaluation.

## Features supported by the current DFS projection

The following are proposed signals grounded in the [existing index proposal](dfs-object-search-index-design.md), not fields already deployed or learned relevance rules. Native LTR supports query-derived scores and scripted features. [8.16 feature examples](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/reranking/learning-to-rank-model-training.asciidoc#L30)

| Signal | Available basis and boundary |
| --- | --- |
| Exact basename match | `name.keyword`; preserve exact identity semantics separately from friendly search normalization |
| Name relevance / phrase match | `name`; prefix relevance needs the additional prefix representation chosen by the analyzer design |
| Content relevance / phrase match | `content_text`, with missing-content behavior defined |
| Query coverage | Matched-term counts and query length computed consistently from the selected search analysis |
| Recency | `mtime_ms` plus request time; clamp/transform deliberately and define missing values |
| File-type preference | `mime_type` and `kind`; explicit user filters remain hard constraints |
| Folder affinity | `ancestor_ids` plus query context, only inside the authorized search scope |
| Size-related feature | `size_bytes`; logical file size is not extracted text length and should not be treated as equivalent |

The proposal does not contain click counts, per-user opens, author, favorites, or historical query/document judgments. `atime_ms` is not a substitute for per-user engagement, and `projected_at` describes indexing activity rather than document relevance. Source-only timestamps such as `created_at_ms` currently disable indexing and doc values; do not assume cheap script access without changing the feature implementation.

Before adopting LTR, build representative judgments for filename lookup, prefixes, content questions, missing extraction, long files, and directory results, covering both human and LLM queries. Keep feature extraction consistent between training and inference. Those measurements should choose retrieval fields, weights, and candidate-window size. [8.16 training guidance](https://github.com/elastic/elasticsearch/blob/v8.16.0/docs/reference/reranking/learning-to-rank-model-training.asciidoc)

## Highlighting with a catch-all

Highlighting needs the actual field value, from a stored field or `_source`. A copy-only catch-all is absent from normal `_source`, so do not expect it to provide snippets unless its text is also stored. Prefer snippets from `name` and `content_text`. With a catch-all search query, explicitly design the highlighting query or field-matching behavior. Rescore queries are not included automatically; `highlight_query` can include the relevant retrieval and rescore clauses. [8.16 highlighting](https://www.elastic.co/guide/en/elasticsearch/reference/8.16/highlighting.html)

The source establishes the length-normalization and eligibility tradeoffs above. It does not establish the winning weights, latency, relevance metrics, or benefits of learned ranking for this dataset.
